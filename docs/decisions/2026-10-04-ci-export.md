# CI export instead of a local template install

Date: 2026-10-04

## Context

The project had no `export_presets.cfg` at all, and
`%APPDATA%\Godot\export_templates\` existed but was empty. So the project
could not be built in any form: every `--export-release` call had no template
to run against.

Two presets were added, `Web` and `Windows Desktop`.

## Why CI and not a local install

The export templates are a 1,222 MB download, and the machine this was done on
was on a slow link.

The repository is **public**, so GitHub-hosted runner minutes are free and
unmetered. `.github/workflows/export.yml` therefore downloads Godot and the
templates on a runner and builds there.

This does not remove the need for a local install. It means nobody has to block
on it to get a build. The templates were installed locally afterwards anyway,
and that turned out to matter: the first local export found a broken scene that
CI had passed. See "The bug CI passed" below.

**A correction on the numbers.** This was originally justified by measuring
**14 KB/s** and extrapolating to ~25 hours. That was wrong. The transfer spent
its first minutes in a slow patch and then sustained **230-250 KB/s**; the real
remaining time was about 68 minutes. CI was still the right call, but it was
argued for on a bad number, and a collaborator reading that line would have
drawn the wrong conclusion about their own connection.

## What the web preset has to get right

Web is the preset that serves the original requirement, that the game run on
any device. One HTML build covers Windows, Mac, Linux, tablets and phones with
nothing installed, which matters where students cannot install software.

| Setting | Value | Why |
|---|---|---|
| `variant/thread_support` | `false` | Threaded rendering needs `SharedArrayBuffer`, which browsers only expose when the page is served with `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`. GitHub Pages and itch.io cannot be made to send those, and a threaded build served without them **fails to a blank screen**. |
| `progressive_web_app/ensure_cross_origin_isolation_headers` | `false` | Injecting those headers from the page does not work and only produces console errors. |
| `html/canvas_resize_policy` | `2` (Adaptive) | The canvas fills the browser window instead of locking to 1280x720 behind black bars on a phone. |
| `vram_texture_compression/for_desktop` | `true` / mobile `false` | S3TC/BPTC is not on every web device; enabling mobile would also demand ETC2/ASTC. |
| `progressive_web_app/enabled` | `true` | Makes the build installable as a PWA. |

The project was already web-viable and this preserves it:

- The renderer is `gl_compatibility`, the only renderer the web platform
  supports.
- Every cutscene is `.ogv` (Theora). Godot excludes the FFmpeg module from web
  builds, so `.mp4` would not have decoded in a browser. When the unreferenced
  `.mp4` files were removed in `ad19f48`, the files kept were the ones that
  actually work on web.

## Three things the workflow does that a naive one does not

**1. `godot --headless --import` runs before the export.**
A fresh CI checkout has no `.godot/`, so no imported assets and no script class
cache, and every `class_name` fails to resolve. This is the same defect that
made a fresh clone fail 19 of 20 tests locally, fixed in `7080be5`. A CI runner
is a fresh clone with a slower network.

**2. The export step disables errexit while capturing output.**
GitHub runs `run` steps under `bash -e`, so a failing export would abort the
step and discard the stderr that was being fetched. The step captures, prints,
then exits with the engine's own code so it still fails.

**3. Success is decided by the artifact, not the exit code.**
Godot has been seen to exit 0 having written nothing.

## Two failures worth recording

**The default branch was an empty placeholder.** `origin/main` was GitHub's
auto-created `Initial commit` from 19 July, containing exactly one file, a
Godot **3-era** template `.gitignore`. All 37 commits of work lived only on
`progress-two-emcsem`, so anyone who cloned the repo got 1 file instead of
5,684 and the whole handoff premise failed regardless of templates. Fixed with
`git push --force-with-lease origin progress-two-emcsem:main`. `--force-with-lease`
rather than `--force` because it refuses if `main` moved since the fetch, so it
cannot clobber unseen work. The placeholder remains recoverable at `21ef860`.

**The first web "failure" was a broken check, not a broken build.**
The verify step rejected `index.html` at 5,546 bytes as "implausibly small".
That is the correct size for a Godot web `index.html`: it is a small HTML shell
that loads `index.js`, `index.wasm` and `index.pck`, and the game is in the
`.pck`. The check measured the one file in the bundle that is meant to be tiny,
so a perfectly good build was reported broken. The matrix now carries a
`verify_file` and `min_mb` per leg, and a `required_files` list, so web
measures `index.pck` and requires all four bundle files to exist.

Also: the error-log scan now runs only on failure. Matching `/error/` alone
fired on the *successful* Windows build, because Godot's progress output
mentions error counts, which made a green job look suspect.

## The bug CI passed

Installing the templates locally and running `tools/build-export.ps1` produced
an error that **both CI legs had shipped without noticing**:

```
ERROR: res://scenes/programming_lab_level.tscn:28 - Parse Error:
Can't create sub resource of type 'CollisionShape3D' as it's not a resource type.
ERROR: Failed loading resource: res://scenes/programming_lab_level.tscn.
```

`CollisionShape3D` is a `Node`, not a `Resource`, so it can never be a
`sub_resource`. The declaration was also dead - `CS_floor` had one occurrence in
the repository, its own definition, and zero `SubResource("CS_floor")` references,
because the floor's collision already existed correctly as a real node at line 45.
Deleted in `137519e`. Both presets then built with zero stderr.

**Why CI missed it.** The workflow's log scan is `grep -Ein 'error:|...'`, which
is case-sensitive, and Godot emits `ERROR:` in uppercase. The scan passed a build
containing a broken scene. `tools/build-export.ps1` matches case-insensitively
and flagged it on the first run.

This is the argument for running the local script at least once rather than
trusting the green tick. The CI check verifies *that the export ran*; the local
script verifies *what came out*.

## Verified locally

With templates installed (`4.7.2.stable`, 35 files):

```
OK    Web                      293.2 MB across 18 files
OK    Windows Desktop        376.8 MB  (one self-contained .exe)
```

**The Windows build was launched.** Unattended, `--headless --quit-after 180`,
it printed the engine banner and exited with zero errors on stdout and stderr:
the pack loads and the autoloads initialise.

**The web build was launched in Chromium.** Console:

```
Godot Engine v4.7.2.stable.official.ed1daf0bf
OpenGL API OpenGL ES 3.0 (WebGL 2.0 (OpenGL ES 3.0 Chromium)) - Compatibility
Build configuration: Emscripten 4.0.20, single-threaded, no GDExtension support.

`single-threaded` confirms `thread_support=false` took effect, which is the

to `SharedArrayBuffer` or `crossOriginIsolated`, so the build has no COOP/COEP
dependency and will run on any static host.

Then, rather than trust a screenshot, the drawing buffer was read inside a
`requestAnimationFrame` callback - a WebGL canvas is only readable in the same
frame as the draw. Sampling a 256x144 block:

| Measure | Value |
|---|---|
| Non-black pixels | 100% |
| Non-zero alpha pixels | 100% |
| Distinct colours | 4,285 |
| Max channel value | 195 |
| `glGetError()` | 0 |

Thousands of distinct colours with no transparent or black void is rendered
imagery, not a blank canvas. The canvas came up **1375x885** rather than
1280x720, confirming `canvas_resize_policy = 2` (Adaptive) fills the browser

```

project code, and does not stop rendering.

### Getting the web build to load locally

`res://` aside, the browser needs a server that handles HTTP Range and serves
concurrent requests. Two harnesses failed before one worked, and both failures
looked like build defects:

1. A sequential `HttpListener` loop serialised the engine's parallel fetches of
   `index.js`, `index.wasm` and `index.pck`. The browser timed out waiting and
   reported `net::ERR_ABORTED` on the wasm. **A server that cannot serve three
   requests at once will make any Godot web export look broken.**
2. A `.NET Task`-based version using `GetNewClosure()` did not execute at all in
   Windows PowerShell 5.1, and served nothing.

What works is Python's `ThreadingHTTPServer` with a Range-aware `send_head`, and
it is now checked in as **`tools/serve-web.py`** so a collaborator does not have
to rediscover this:

```
python tools/serve-web.py --root build/web
```

Four parallel 4 MB range requests complete in 0.6 s. Note that this machine has
no usable `python` on PATH - the Microsoft Store stub exits 9009 - but Blender
ships a real CPython 3.11, which is what the checks above used:

```
C:\Program Files\Blender Foundation\Blender 5.0\5.0\python\bin\python.exe
```

Any Python 3.7+ will do; the script has no third-party dependencies.

When testing a web build, **confirm the server can serve parallel range requests
before concluding anything about the build.** A harness that cannot do that will
manufacture a failure that looks exactly like a broken export.

## Web-hostile APIs, checked statically

Grepped `scripts/` and `scenes/` for the things that break on web:

| Pattern | Hits | Assessment |
|---|---|---|
| `OS.execute` / `create_process` | 0 | Safe. No shelling out. |
| `OS.get_executable_path` / `get_user_data_dir` | 0 | Safe. No absolute paths. |
| `Thread` / `Mutex` / `Semaphore` | 0 | Safe, and moot with threads off. |
| `JavaScriptBridge` | 0 | Nothing web-specific to break. |
| `DirAccess` | 8 | All `user://` or `res://` via `ProjectSettings.globalize_path`. Works on web's IndexedDB-backed `user://`. |
| `DisplayServer.window_set_mode(FULLSCREEN)` | 1 | Works on web; the browser handles the permission prompt. |
| `VideoStreamPlayer` | 2 cutscene players | `.ogv` only, so the Theora module covers it. Autoplay with audio still needs a user gesture. |
| `FileDialog` | 21 | **The real risk.** `ACCESS_RESOURCES` on web cannot enumerate a real filesystem. Affects `flowchart_editor.gd`. |

## Also found, not acted on

`scripts/platform.gd` provides `is_desktop_build()`, `is_mobile_or_web()`,
`wants_touch_controls()` and `show_desktop_settings()`, with a
`emc/simulate_mobile` override for desktop testing. **Nothing calls any of
them.** The abstraction was written and never wired up.

And the input map is keyboard-only: 7 actions, 11 `InputEventKey` events, zero
`InputEventJoypadButton`, `InputEventJoypadMotion`, `InputEventScreenTouch` or
`InputEventMouseButton`. So "compatible for any device" is currently false at
the input layer regardless of how well the export works.
