# Full project audit — 2026-10-05

Scope: every tracked file in this Godot 4.7 project. Engine: 4.7.2.stable.official.

## Method, and why

Deterministic scanners plus engine-as-authority, not reading 271 scripts by hand.
Hand review does not scale and reliably misses dangling references — which is
exactly the bug class already found once in this repo (the dead `sub_resource`
in `programming_lab_level.tscn` that CI's case-sensitive grep passed).

Three tools, all reproducible from a clean checkout:

| Tool | Question it answers |
|---|---|
| `tools/audit_dump.gd` | Does the engine load every script, scene, resource, shader? |
| `tools/audit_nodepaths.py` | Does every `$Path` / `%UniqueName` in a script resolve in its real scene tree? |
| `tools/audit_refs.py` | Do every `ext_resource` path and uid resolve? What is referenced by nothing? |

`tools/fix_ext_resource_paths.py` — uid-driven repair for the stale paths found below.

Two rules the tools follow deliberately:

- **No instantiation.** `audit_dump.gd` reads `PackedScene.get_state()` instead of
  calling `instantiate()`. Instantiating runs `_ready`, which writes saves,
  triggers `SceneTransition` and mutates `LevelProgression`. An audit must not
  change what it measures.
- **Scanners run from the project root**, and their output is split by path
  before drawing conclusions. Raw counts are ~97% `addons/` and `vendor/` noise.

### 4b — typed in a later pass. 44 of 51 done, 7 documented exceptions.

The scanner needs a root argument. Without one it defaults to `"."` relative to

### 4c — the first attempt broke dialogue. The gate caught it; a code read would not.

Typing `get_dialogue_lines() -> Array[Dictionary]` compiled clean and looked
right — `entry.get("dialogue", [])` really does yield a list of line dicts.
It still failed, at runtime, in `test_e_key_double_fire.tscn`:

```
SCRIPT ERROR: Trying to return a value of type "Array" from a function whose
return type is "Array[Dictionary]".
```

**Godot does not implicitly convert an untyped `Array` to `Array[T]` on
return.** The JSON array is a plain `Array` at runtime; the typed return is a
promise the value cannot keep. Same for `get_choices()`, and therefore for
`dialogue_ui._dialogue_lines`, which is fed by both.

Reverted to untyped. Net: 4 fewer containers typed than the 48 claimed above,
all of them on the dialogue path.

The lesson generalises: **a typed container is verified by running the code, not
by reading it.** Every other edit in this pass happened to be a literal
initialiser (`= []`, `= {}`) whose type is obvious at the declaration, which is
why they survived. `flowchart_workspace.placed_nodes` was the other risky one —
it is `Dictionary[String, FlowchartNode]` and every writer does pass a
`FlowchartNode`, so that one holds.

Note: `save_manager.gd` carries a UTF-8 BOM. A PowerShell `Set-Content`
round-trip silently stripped it, which `git diff` showed as a changed first
line. Restored from raw bytes; the edit pass afterwards read/wrote bytes
directly and preserved BOM + line endings.

### 5a. Root cause of the three crashes — every undoable action destroys the object graph

`ModelingAction._apply()` (`scripts/modeling_lab/commands.gd:91`):

1. free every node in `remove_ids` by instance ID
2. free any node whose display name matches a snapshot entry
3. re-materialise every object from the snapshot

So a move, a scale, a rename or a reparent **frees and recreates every
`MeshInstance3D`**. `transform_manager.end_move()` documents this and works
around it:

```gdscript
# The command rebuilds node instances (frees originals, materializes
# fresh copies). Re-point the selection onto those new instances so the
# gizmo keeps tracking live nodes instead of silently going stale.
_selection_manager.reselect_from_ids(action.get_last_created_ids())
```

The selection manager is patched. **Nothing else is.** Any other holder of a node
reference dangles — the three crashing tests are just the first to notice.

Consequences beyond the tests:

- Signal connections to a lab object are lost on every transform.
- `_primitive_locked` and `_scores`, which hold per-object references, go stale.
- Runtime state on the node (materials, metadata) is rebuilt from the snapshot.
- Every gizmo drag releases through a full scene-graph rebuild.

The trade-off, stated plainly: snapshot-based undo is a legitimate pattern, but
it belongs on the **undo** path. A forward move/scale/rename only needs property
mutation. Rebuilding on execute is what makes references unsafe. If the snapshot
is kept for undo and the forward action mutates in place, the dangling-reference
class disappears without touching undo semantics.

#### 5a-i. FIXED — transform and rename now mutate in place

`ModelingAction` now dispatches `transform` and `rename` to `_apply_transform()` /
`_apply_rename()` instead of the generic rebuild. Only `spawn`, `delete`,
`duplicate`, `group` and `ungroup` still create or destroy nodes, because only
those need to.

The `material` action was already doing this, via `_apply_material()` →
`_material_mgr.apply_to()` — the working example was in the same file.

Nodes resolve through `_resolve_live_node()`: the instance IDs captured at
command-build time still point at the same instances, with a display-name lookup
as fallback for the case where something outside the command system freed and
recreated the node. Undo still replays the same snapshot; it just writes it onto
the surviving node.

Renaming now goes through `HierarchyManager.set_blender_name()`, which sets
`node.name` alongside the `blender_display` meta. Previously the rebuild wrote
the snapshot's unchanged `name` field, so `node.name` went stale while the
Blender-style display name updated — a second latent bug this fixed.

### 5b. `test_modeling_parent_group` — 3 genuine assertion failures — FIXED

```
FAIL: unparent leaves b in its group
FAIL: second Parent should create 'group.001'
FAIL: first group still named 'group'
```

All three were one root cause plus two more that the fix exposed.

**Root cause.** `_on_hierarchy_unparent` called `CommandFactory.ungroup()` on each
former parent. `_execute_ungroup` promotes **every** member to the container and
frees the group. The spec in the test header is Blender's *Clear Parent*: only the
selected objects leave, and the group stays behind even when empty.

In-game this was destructive: selecting **one** object inside a group and pressing
Unparent destroyed the whole group and scattered its remaining members to the top
level. All three failures followed from that — `b` was gone with the group, so the
name `group` was released and the next group reused it instead of `group.001`.

**Fix.** New `CommandFactory.reparent()` + `ModelingAction._apply_reparent()`:
moves named nodes to a target parent in place via `reparent_preserve()`, with the
`before` snapshot carrying each node's original `parent_path` so undo is the same
operation pointed backwards. Distinct from `ungroup`, whose undo restores *all*
members and so cannot express a partial detach.

**Two further bugs the new test coverage exposed:**

1. `_on_hierarchy_parent` carried the comment `# Generate a unique group name` and
   then did `var group_name := "group"` — `allocate_name` was never called. The
   second group collided, Godot renamed the *node*, and the `blender_display` meta
   stayed `"group"`, so `group.001` never existed.
2. `_undo_group` and `_execute_ungroup` located their group via
   `_find_ungroup_target()` — "first non-mesh child of the container" — even though
   both commands are *constructed* with a specific group. With two groups present,
   undoing `group.001` dissolved `group`. Replaced by `_resolve_group_node()`,
   which prefers the instance ID recorded when the action ran and falls back to the
   uniquely-allocated display name in the snapshot. `_find_ungroup_target` and
   `_collect_meshes` became dead and were deleted.

**Behaviour note.** Nothing can select a group node — groups are plain `Node3D`
while the selection model is `Array[MeshInstance3D]`, and `_collect_from_node`
recurses *into* groups to harvest their meshes. So the old "dissolve" path was
only ever reachable by selecting a *member*, which is precisely the case that must
now be Clear Parent. Consequence: **an emptied group can no longer be dissolved
from any button.** That follows the spec ("empty groups stay behind"), but removing
one now needs a new affordance. Flagged, not designed — see Open.

Verification: 3 failing → `PASS: parent/group + Blender naming`. Test extended to
cover undo of detach and the emptied-group case.

### 5c. `test_programming_lab` - `level_completed` never fires - FIXED (test was wrong)

Not a product bug. `_on_lab_exit` completes the lab only when every entry in
`puzzle_scores` is non-zero:

```gdscript
var all_solved := puzzle_scores.size() > 0
for s in puzzle_scores:
    if s == 0:
        all_solved = false
        break
if all_solved and level_def and not level_def.level_id.is_empty():
    LevelProgression.complete_level(level_def)
```

The test called `_on_lab_exit()` on a freshly-loaded lab — all 7 scores zero —
and asserted `level_completed` had fired. Exiting without solving anything
correctly does *not* complete a level, so the assertion could never pass. It had
been failing in the gate for the whole time, for a correct reason.

Fixed by testing the behaviour rather than the wish: the exit is now driven with
the scores a finished sequence leaves behind.

Two things this cost, both worth recording:

- **A second `await` was needed.** The first rewrite hung the process. Cause:
  `_on_lab_exit` ends in `change_scene_to_file`, which frees the current scene —

  process never quits. `tree` is now captured before the exit.
- **The negative direction could not share the file.** Since an exit can only be
  driven once per process, both directions in one harness means one is never
  actually exercised. Mutation-tested: deleting the `all_solved` check left the
  single-file version **green** while every lab exit completed the level. Split
  into `test_programming_lab_unsolved.{gd,tscn}`, and that mutation now fails it.
  Completion on an unfinished lab is the worse of the two bugs, so it is the one
  worth guarding.

Both halves are now mutation-verified in both directions: dropping the
`all_solved` gate fails the unsolved test, and removing `complete_level` fails
the solved one.

A stale comment in the test named `scripts/programming_lab.gd`, which has not
existed since `042a793` moved it to `scripts/programming_lab/programming_lab.gd`.

The programming lab completes but never emits the signal. Likely the same

### 5d. Joystick hidden while deflected pins the character into a permanent walk - FIXED

Found while adding a debug toggle for the on-screen joystick, not by the audit
scanners — they do not model input state over time.

`game_ui.gd` hides the joystick in two places: when a dialogue starts, and now
when touch controls are toggled off. Neither neutralised the value first. A
hidden `Control` receives no `_gui_input`, so the finger lift that normally
re-centres the stick never arrives, leaving `_value` deflected and `_dragging`
true indefinitely. `PlayerController._physics_process` only adopts `_virtual_move`
when it is *longer* than the keyboard vector, so a stranded value of length 1
outranks WASD and the character walks until the app restarts.

Reachable at HEAD on mobile: one thumb on the joystick, another taps an NPC, the
dialogue opens and hides the stick, the thumb lifts onto a control that is no
longer there.

Fixed by adding `EMCMobileJoystick.reset()` and calling it at both hide sites.
It clears `_dragging`, and emits a zero value only if one was actually held, so
`reset()` on an already-neutral stick (the common case — every dialogue start)
costs no signal emission.

The `dialogue_started` / `dialogue_ended` lambdas became named methods to carry
the comment and the `reset()` call without a three-clause one-liner.

### 5e. Rotate gizmo dead / snapping — and the inspector destroying scale - FIXED

From a play report: "the rotate gizmo does not respond and when rotating the
object reset when using the one in the panel setting additionally when rotating
the object snap randomly back or when moving a rotation is reset."

Four defects, three of them independent of each other:

**Snap applied to the per-frame increment, not the total.** `apply_rotate()` took
the incremental screen delta and snapped it directly: `snap_value(rad_to_deg(d),
15.0)`. `modeling_lab.gd` feeds `0.001 rad/px`, so a 15° detent needed ~262px of
drag and anything shorter rounded to **zero**. The object sat still for the first
131px, then jumped a full 15°, and dropped back to 0° the moment the cursor
returned inside that band. That is both "does not respond" and "snaps randomly
back" — one cause, two symptoms. Sensitivity also raised 0.001 → 0.004 rad/px
(~390px per 90°) with the user's agreement; at the old rate a full turn needed
~5,600px.

> **Correction (second play report, "harder to control… if I try to move it back
> it continues moving forward").** The write-up above diagnosed this as a snap
> scope problem and fixed it by *accumulating* the gesture angle. **That fix was
> wrong and introduced the bug the user then reported.** The premise — that the
> handler sends an increment — was false. `_drag_start_mouse` is captured at
> press, so `(mouse_pos - _drag_start_mouse).dot(perp) * SENSITIVITY` is an
> **absolute offset from the grab point**, and it had always been snapped as a
> total. The genuine problem in the original code was only the 0.001 rad/px dead
> band. Accumulating an already-absolute value re-adds the whole gesture once per
> motion event: rotation accelerated (40px of drag → 22.9° instead of 9.2°), and
> dragging *back* from 40px to 20px went 22.9° → 27.5°, because the accumulator
> only unwinds once the cursor crosses back past the grab point.
>
> Root cause of the wrong fix: the regression test fed *one increment twice* and
> asserted the rotation doubled — which is not the shape the real handler
> produces. The test encoded my assumption instead of the feed. Same class of
> error as the phantom-revert trap below, one level up: I asserted the
> behaviour I had implemented rather than the behaviour the caller drives.
> `tests/test_modeling_rotate.gd` now drives the actual absolute sequence
> (10 → 20 → 30 → 40 → 30 → 20 → 10 → 0 px) and asserts 1:1 tracking and
> reversibility. All three new assertions were confirmed to fail against the
> accumulating implementation before the fix was kept.
>
> `apply_rotate()` now treats the value as absolute. Position and scale snapping
> are unchanged.
>
> **Rotation snap: on, live, 5°.** An interim commit set
> `SnapSettings.rotation_snap_enabled = false` on the reasoning that any detent is
> a dead band. A follow-up request ("rather than snapping after I let go, make it
> snap in real time like the move snap") exposed that this was the wrong call and
> also a wrong description: there was never a deferred snap. `apply_rotate()`
> snaps the total on every mouse-motion event, exactly as `apply_move` snaps
> position, and `end_rotate()` only writes the undo record. Rotation simply had no
> snapping at all. Re-enabled, at **5°** rather than the Blender/Maya 15° — at
> 0.004 rad/px one pixel is 0.229°, so 15° needed ~65px of drag per detent and a
> ±32px dead band, which is what read as "harder to control"; 5° is ~22px per
> detent and ±11px of stall. Asserted mid-drag in
> `tests/test_modeling_rotate.gd::1d`, since a release-time snap would satisfy a
> post-drag assertion.

**Inspector rotate discarded scale.** `_on_inspector_rot_changed` rebuilt the
basis with `Basis.from_euler(...)` alone. Scale lives in the basis, so rotating a
scaled object reset it to unit size — "when rotating the object reset when using
the one in the panel setting".

**Both inspector handlers used the wrong multiply order.** They called
`Basis.scaled(s)`, which **pre**-multiplies (`S * basis`). That is only correct
while the incoming basis is a bare rotation. Once it carried scale, the row
lengths multiplied instead of being replaced: setting X to 5 on a (2,3,4) object
produced **(10, 9, 16)** — the untouched axes corrupted too — and a second edit
squared them. Fixed to build `orthonormalized() * Basis.from_scale(s)`, and the
rotate handler to `Basis.from_euler(r) * Basis.from_scale(s)`. Both now read the
scale from `sel.scale` rather than `basis.get_scale()`, so that the scale is read
through Node3D's own decomposition rather than re-derived from the basis.

> **Correction (5h):** the parenthesis here originally claimed
> "`basis.get_scale()` returns row lengths and is only the true scale while
> unrotated (it reported (2,3,4) under yaw as (3.16,3.0,3.16))". **That claim is
> wrong.** Measured in 5h, `basis.get_scale()` returns `(2,3,4)` correctly under
> yaw — row lengths are the scale for `R * S`, and the `S * R` vs `R * S`
> confusion is what produced the (3.16, 3.0, 3.16) figure. Reading scale from
> `sel.scale` is still the better choice (Node3D owns that decomposition), but the
> justification for it was false, and it sent me looking at scale rather than
> `get_euler()` when 5h was reported. The real cause of that (2,3,4)→(3.16,3.0,3.16)
> result was `Basis.scaled()`'s pre-multiply, exactly as the paragraph above says.

**Not a bug: "moving resets a rotation".** `apply_move` only touches `.position`.
That symptom did not reproduce and no code change was made for it. What the user
was seeing was the snap dead-zone plus the corrupting inspector scale: the
orientation never changed, but the basis was being silently mangled by the same

`tests/test_modeling_rotate.gd` covers all of it. One trap worth recording: the
first version of that test reported a convincing phantom — "the scale command is
correctly applied, then reverted one frame later" — with an extra `transform`

`get_stack()` trace on `execute_command`, which showed the revert coming from
`_test_move_does_not_reset_rotation` — the test's own line 180. Fixed by
`await`-ing every sub-test. Debug output filtered through `Select-String` also
hid this by interleaving; the raw file had to be read directly.

### 5f. Gizmos dead whenever an axis is parallel to the view - FIXED

From a play report: *"bug when using the ViewOrbitGizmo the rotate gizmo stopped
working, or when looking straight to the object, and at other moments I can't
use any of the gizmos in the object."*

One root cause, three tools. `_compute_drag_screen_basis()` derived a handle's
screen direction by unprojecting the gizmo centre and the centre displaced along
the handle's world axis:

```gdscript
var origin := camera.unproject_position(gizmo.global_position)
var tip    := camera.unproject_position(gizmo.global_position + _drag_axis)
_drag_axis_screen = (tip - origin).normalized()
_drag_axis_perp   = Vector2(-_drag_axis_screen.y, _drag_axis_screen.x)
```

When the axis is parallel to the view ray both points project to the **same
pixel**, so the delta is `(0, 0)` and `.normalized()` returns `(0, 0)`. Every
`moved.dot(...)` downstream is then exactly 0: the handle is picked, dragged, and
nothing happens. `_drag_axis_screen` feeds move and scale, `_drag_axis_perp`
feeds rotate — hence "any of the gizmos".

Measured, before the fix:

| view | projected length | rotate delta | move delta |
|---|---|---|---|
| `set_view_axis(UP)` | 0.0000px | 0.000 | 0.000 |
| `set_view_axis(RIGHT)` | 0.0000px | 0.000 | 0.000 |
| `set_view_axis(BACK)` | 0.0000px | 0.000 | 0.000 |
| default tilted view | 45–90px | works | works |

This is why it read as intermittent. `ViewOrbitGizmo`'s axis buttons call
`CameraController.set_view_axis()`, which aligns the camera to the axis
**exactly** (dot product 1.000 at every one of the six axis buttons), and
hand-orbiting reaches the same alignment. The default camera is a tilted 3/4
view where all three axes project fine.

ViewOrbitGizmo was *not* blocking input — its `Control` is a correct 120×120 in
the top-left corner and the object at screen centre is well outside it. It only
*caused* the bug by calling `set_view_axis`.

Fixed by branching on the projected length: above ~4px nothing changes; below it
the basis falls back to the screen radius from the gizmo centre to the grabbed
point, and its perpendicular. For rotate that fallback is not merely safe but
correct — the ring is face-on in this situation, so the tangent to the ring at
the cursor *is* the direction the ring travels under the cursor. A final
`Vector2.UP` covers a grab within a few pixels of the centre.

New test `tests/test_modeling_gizmo_degenerate_view.gd` drives the production
helper across all six view-axis alignments × three handles × three tools.
**26 assertion failures before the fix, 0 after.** It asserts the basis vectors
are unit length (the defect stated directly) *and* that the object actually
rotates/moves/scales end-to-end through `TransformManager`.

Two things worth recording from building it:

- **A stale node reference, not a product bug.** `end_move`/`end_scale`/`end_rotate`
  each push an undo command, and the command layer re-points the selection at
  rebuilt instances. A `cube` captured in `_ready` goes stale after the first
  sub-test, so reads against it compare a detached node and every later
  assertion reports a phantom "no change". Same family as the phantom-revert trap
  in 5e; the fix is `_live()` re-fetching each time.
- **A radial drag is legitimately inert.** The first version of the test dragged a
  fixed `(100, 100)`, which for a face-on ring happened to run almost exactly
  along the radius, so it produced 0.5px of tangential travel and the 0.1 scale
  snap rounded it away. That read as "still broken" but was correct behaviour.
  The test now builds drags *along the axis under test*.

### 5g. Rotate reverses when the ring faces the camera - FIXED

Play report: *"bug in certain angle or at the focus in positive x y z the rotation
is reverse in negative it rotates fine"*.

**Not the same bug as 5f, and the 5f fix did not touch it.** 5f was a *degenerate
basis* — zero-length, so the handle did nothing. This is a *wrong-signed* basis:
the handle responds, and turns the wrong way.

**Root cause.** Rotate derived its screen direction as the perpendicular of the
projected axis, the same quantity move and scale use. The perpendicular of the
projected axis is **not** the tangent to the rotate ring. It agrees only when the
axis points *away* from the camera.

Measured across 6 axis-aligned views × 3 handles × 8 ring angles × 6 drags:

| ring's axis vs camera | cases reversed (of 48) |
|---|---|
| points away (`axis · view > 0`) | 0 |
| points at the camera (`axis · view < 0`) | **36** |
| edge-on (`axis · view == 0`) | 16 |

That is exactly the report. `ViewOrbitGizmo`'s `+X`/`+Y`/`+Z` buttons each call
`CameraController.set_view_axis()` with the *positive* axis, putting the camera on
that axis's positive side — so the ring faced the user and reversed. The negative
buttons put the camera on the far side and happened to come out right. Hence
"positive reverses, negative fine". The edge-on column is why "certain angle"
appeared too: the default camera (`_orbit_rot = from_euler(0.4, 0, 0)`) gives a
view direction of `(0, 0.389, -0.921)`, so `|RIGHT · view| == 0` **exactly** — the
X ring is edge-on from the default view, before the user touches anything.

**Fix.** Rotate no longer derives its tangent from the projected axis. A ring point
at angle `t` sits at `centre + u·cos(t) + v·sin(t)` with `v = n × u`, so on screen
it traces `C + U·cos(t) + V·sin(t)` and its tangent is `-U·sin(t) + V·cos(t)`.
`pick()` already computed the exact 3D point the raycast struck and discarded it;
that point gives `t` exactly, in the same `(u, v)` frame `U` and `V` were projected
from, with no degeneracy to guard at any angle. `gizmo_3d.pick()` now returns
`position`, and the press handler passes it through.

**Three alternatives were implemented and measured, and all were worse** — recorded
because each is a plausible-looking fix that does not work:

- *Screen-space 2×2 solve* for `t` against `U, V`. Degenerate at edge-on: `U × V`
  is the signed area of the projected ellipse and vanishes exactly there. Left
  **155** reversals of 1152.
- *Arcball angle* in a ring-aligned basis (`right = view_dir × axis`). Well
  conditioned at edge-on, but `(right, up)` is **camera-dependent** while `u, v`
  here are an arbitrary fixed choice, so the offset between the frames flips sign
  as the camera moves. Whole view/handle pairs reversed **48 of 72**. Also, `up` is
  exactly `-view_dir` at edge-on, so projecting the basis into screen space
  degenerates too — it has to read the cursor's 3D ray direction instead.
- *Camera-ray ∩ ring plane.* At edge-on the camera lies **in** the ring plane, so
  `ray · n == 0` for every ray and the solve is exactly as degenerate as the
  screen one. Measured **327** of 1152 — worse than the screen solve.

Also fixed in passing: the raycast hit was being computed and thrown away on every
gizmo press.

**Result:** 1728 combinations (8 views × 3 handles × 12 ring angles × 6 drags),
**1 reversal, and that one is -1.16px on a 30px drag** — 3.9%, which is the
second-order error of a first-order model, not an inversion. The regression test
asserts `follow > -10%` of the drag, and an actual inversion moves the grabbed point
-100% (measured -137px on a 20px drag), so the regimes do not overlap.

**Test fails before the fix, confirmed:** with only the one production line
reverted to the projected-axis perpendicular, the suite reports **362 reversal
failures**; with the fix, **0**.

### Two methodology traps this bug exposed

- **The ground truth must be what the user actually grabbed.** My first version of
  the criterion placed the grabbed point at an arbitrary angle on the *idealised
  centreline* ring. That is wrong when the ring is edge-on: both halves project to
  the same pixels, so the user necessarily grabs whichever half is in front, and
  grading against an arbitrary half **fails a correct implementation**. That error
  alone reported 157 spurious failures on correct code. The test now rotates the
  point `pick()` actually hit.
- **A drag large enough to leave the tangent's valid range invalidates the
  criterion.** At 120px the drag implies `phi ≈ 27°`, and on a foreshortened ring
  27° of real rotation legitimately carries the point *backwards* relative to its
  instantaneous tangent. That was a flaw in the measurement, not the product: the
  same code scored 0/48 and 24/48 on identical geometry depending only on drag
  size. The test now uses 20px (~4.5°). This is the same lesson as the earlier
  rotate fix: assert the feed the real handler produces, not a feed invented for
  the test.

### 5h. Move and scale rotate the object - FIXED

**Report:** "bug when moving or scaling the object it will rotate".

**Root cause — `Basis.get_euler()` on a basis that carries scale.** Not the
gizmo, not `apply_move`, and not the basis math. `CommandFactory.transform()`
serialised a `Transform3D` into `position` + `rotation_degrees` + `scale`, and
took the euler angles out with `basis.get_euler()`:

```gdscript
b_data.rotation_degrees = Vector3(rad_to_deg(b_euler.x), ...)
b_data.scale = b_t.basis.get_scale()
```

`Basis.get_euler()` is only valid on an **orthonormal** basis. On `R * S` it
returns the wrong angles. Measured:

| node rotation | scale | `get_euler().x` returned | correct | error |
|---|---|---|---|---|
| (45, 45, 0) | (1.5, 1.5, 1.5) | **90.00°** | 45° | 45.0° |
| (45, 45, 0) | (2, 1, 0.5) | 20.70° | 45° | 24.3° |
| (30, 20, 10) | (2, 1, 0.5) | 14.48° | 30° | 15.5° |
| (30, 20, 10) | (3, 2, 1) | 7.1° | 30° | 22.9° (see below) |
| (45, 45, 0) | (1, 1, 1) | 45.00° | 45° | 0 |

`basis.get_scale()` was **not** at fault — measured exact for `R * S` in every
case (the stored scale matched `node.scale` throughout). Note the audit's own
note in 5e — "`get_scale()` is row lengths, valid only while unrotated" — is
**wrong**, and that wrong belief is what sent me looking at scale instead of
euler first. Row lengths are the scale for `R * S`; the row/column
confusion only bites for `S * R`.

**Why it hit a live drag and not just undo.** Every gesture ends in
`end_move()` / `end_scale()` / `end_rotate()`, which build the snapshot and then
`_undo_redo.execute_command(action)` — which **executes it**. So the lossy
decomposition rewrote the object at the end of every single drag. A move,
whose own code (`apply_move`) touches only `.position`, rotated the object on
commit. That is the report, and it is why "moving or scaling rotates it" while
`apply_move` provably never writes rotation.

**Fix.** The snapshot already receives a full `Transform3D`; nothing was lost by
serialising it. `CommandFactory.transform()` now stores the basis verbatim in a
new `basis` key (via `_snapshot_transform`), and `_apply_transform()` writes the
whole local transform in one assignment when that key is present:

```gdscript
node.transform = Transform3D(entry["basis"], entry.get("position", Vector3.ZERO))
```

One write also means no intermediate basis is observable mid-assignment.
`rotation_degrees` / `scale` are still populated in the snapshot, now derived
correctly (`orthonormalized().get_euler()`), so the dictionary stays
self-describing and the three-property path remains as a fallback for the
hand-built snapshots in `test_undo_redo_commands.gd`.

**Rejected alternative:** orthonormalise before extracting euler
(`basis.orthonormalized().get_euler()`) and keep the three-property write. This
recovers the rotation exactly — but measured, it still fails for
**non-uniform** scale (`delta 1.06` at (45,45,0)/(2,1,0.5)), because
`Basis.from_euler(e).scaled(s)` is `S * R` while `Node3D` needs `R * S`. Correct
on uniform scale, wrong on the case that matters. Storing the basis is both
simpler and unconditionally exact.

**Test:** `tests/test_transform_commit_fidelity.tscn`. Asserts the invariant
rather than a formula — *a move cannot change the basis at all, and a scale can
only change column lengths* — across 5–6 rotation/scale configurations
including the 46°-error case.

**Fails before the fix, confirmed:** **15 assertion failures**, up to **46.0°**
of phantom rotation (matching the predicted `get_euler` error exactly, which
confirms the mechanism rather than merely the symptom). After the fix: **0**.

**Why the 5e test missed this for a whole session.** `test_modeling_rotate.gd`
checks that a move preserves rotation using a **30° Y-only** rotation on a
(2,3,4) scale. `get_euler()` happens to be exact for single-axis Y — the error
needs rotation on more than one axis. A test that only checks one axis cannot
find a matrix-decomposition bug.

### 5i. Scale acts along local axes while every handle is drawn world-aligned - FIXED

**Not a reported bug.** Found while planning the orientation toggle: the three
transform tools disagreed about what frame they were in.

| | frame |
|---|---|
| `apply_move` - `position += axis * d` | WORLD |
| `apply_rotate` - `rot * _original_bases[i]` | WORLD |
| `_build_*` - handles from `AXES` | WORLD |
| `apply_scale` - `node.scale = s` | **LOCAL** |

So on a yawed object the red X handle pointed along world X while the stretch it
produced ran along the object's own X. Rotate 45 degrees and handle and effect
diverge.

**Fix.** `Gizmo3D.set_orientation/get_orientation/axis_to_world`;
`apply_scale` gains a `world_frame` parameter. Global left-multiplies a diagonal
by the basis (`S * B`, scale along world axes, shear preserved), Local
right-multiplies (`B * S'`, scale along the object's own axes, also shear
preserved). Never `node.scale` - that setter decomposes the basis and discards
shear (measured: a round trip through it moves a sheared basis by 0.707, a
direct basis write by 0). Same bug class as 5h.

**Default is Local, not Global.** Shipped Global first, then reversed - see 5j for
the measurement that prompted it and the decision record for the argument. Both
modes are implemented and the toolbar toggle switches between them; Global is no
longer the default because it skews a rotated object into a parallelogram, and
scale that changes an object's dimensions without skewing it is what was wanted.
The cost is that under Local no world axis is scaled by the factor you typed
(world-X 1.414 -> 1.768 on a 45-degree-yawed cube, where Global reaches 2.121 by
shearing). Recorded as an open third mode rather than silently accepted.

`apply_scale` now scales from **column lengths** rather than `_original_scales`,
the only correct quantity for a sheared basis. For a clean `R * S` basis the
Local path is bit-identical to the old one. `_original_scales` had no other
reader and was removed.

**The two-axes trap.** A handle's axis is needed in two different frames, and
using the wrong one is a real bug rather than a cosmetic one:

| consumer | axis |
|---|---|
| `apply_scale` component pick | **local** - picks *which* of X/Y/Z was grabbed |
| `_compute_drag_screen_basis` | **world** - projects a real world point |
| `apply_move` / `apply_rotate` | **world**, frozen at press |

Under Local a 45-degree-yawed local-X handle has a world direction with *both* x
and z non-zero, so passing the world axis to `apply_scale` would scale two axes
at once.

**Three things the plan got wrong, all caught by testing:**

1. *Predicted the per-frame sizing would clobber the orientation.* It does not.
   `Basis.set_scale` preserves the rotation part; reverting the implementation to
   a plain `.scale` write still left the orientation intact (rotation delta
   0.0000). The write is composed rather than assigned so there is one write
   path, but it is **not** load-bearing - and the test covering it is labelled a
   smoke check precisely because it cannot tell the two apart.
2. *Claimed `_compute_drag_screen_basis` needed no change.* It does. Its first
   implementation split `_drag_axis` into two fields that must agree; anything
   setting one without the other silently produced a zero axis and broke the
   5f/5g rotate regression (3 failures, reversed rings). The screen maths now
   derives from the gizmo at call time; only the motion handler keeps a
   press-frozen axis, because under Local the gizmo frame follows the object and
   a rotate axis recomputed per frame would chase the object it is rotating.
3. *Justified the inspector readout change by claiming `node.scale` is a lossy
   decomposition of a sheared basis.* **Measured false.** `Basis.get_scale()`
   returns the column lengths, equal to the last digit on
   `from_scale(1.5,1,1) * from_euler(0,45,0)` and on a non-uniform variant. The
   readout was never the broken half; switching it changes no displayed value.

   The inspector **write** was genuinely broken, though: it rebuilt as
   `orthonormalized() * Basis.from_scale(s)`, which flattens a sheared basis back
   to `R * S`, so touching the panel destroyed the shear. It now right-multiplies
   by the ratio, scaling one local axis and leaving everything else. Inspector
   fields stay always-local regardless of the gizmo toggle - the `RotX/Y/Z`
   beside them are local Euler angles.

**Display caveat (pre-existing, not fixed):** the Scale fields are `SpinBox`es
with `step = 0.01`, so the panel quantises whatever it is shown. True length
1.05119 displays as 1.05. Editing a field does not write the displayed value
back - the write path recomputes from the live basis - so no drift accumulates.

**Known limits of this change:**

- ~~**Save/load still loses shear.**~~ **Fixed in 5j.**
- **Group spread is still scaled in world space.** `apply_scale` moves members by
  `rel * factor_v`, which is world-space regardless of frame. Pre-existing: Local
  scale against a world-space `rel` was already inconsistent before this change.
  Left alone deliberately as out of scope.
- **Scale feel is unmeasured.** The maths is pinned down; whether a scale drag
  feels right needs a human dragging it.

Verification: `tests/test_gizmo_orientation.gd` - 11 assertions, all green after
a 4-failure RED. Gate after the change: **38 pass, 1 warn (known-flaky
`test_full_lab_sweep`), 0 fail of 39.**

### 5j. Shear was not representable end-to-end - FIXED

5i settled what scale *does*. It left the shear it produces only half-supported:
the object was correct on screen and wrong everywhere else. Two places still
assumed a sheared basis has a TRS representation. Both fixed.

**Measured first, not inferred.** Global X scale of x1.5 on a cube yawed 45
degrees, through the real `apply_scale` path, snap off:

| yaw | world-X extent | world-Z extent | front face | sheared |
|---|---|---|---|---|
| 0 | 1.000 -> 1.500 | 1.000 -> 1.000 | 1x1 -> 1.5x1 | no |
| 45 | 1.414 -> **2.121** | 1.414 -> 1.414 | 1x1 -> 1.275x1, **tilted 11.3 deg** | **YES** |
| 90 | 1.000 -> **1.500** | 1.000 -> 1.000 | 1x1 -> 1x1 (goes deeper) | no |
| -90 | 1.000 -> **1.500** | 1.000 -> 1.000 | 1x1 -> 1x1 | no |

So the invariant is: the world axis you dragged grows by exactly the factor, no
other world axis moves, and anything off-axis is shear. That is Blender's Global
mode, and it is what the implementation already did. Local at the same 45 degrees
grows world-X 1.414 -> 1.768 *and* world-Z 1.414 -> 1.768 — neither world axis
does 1.5, because it stretched the object's own X, which lands diagonally.

**A correction to my own reasoning, worth keeping.** I had assumed `diag(f) * R`
scales column *i* by *f_i*, the way right-multiplication does. It does not: it
scales **row 0** by *f*, i.e. it multiplies every point's world-X coordinate. The
measurement caught it — at 45 degrees the local-X axis went 1.000 -> 1.275, not
1.500. The corrected reading is the correct one for a world-axis stretch, and it
is why world-X extent grows by exactly the factor while world-Z does not move.

#### 5j-i. save/load silently un-sheared every object

`save_manager` stored `rotation_degrees` + `scale` and restored them the same
way. Neither can express a sheared basis — a Global scale is `S*R`, not `R*S` —
so every Global-scaled object came back as its decomposition. Measured: up to
**0.65 per component** of basis error on the restore.

Fixed by storing the basis itself. `PrimitiveSaveData` gains `basis_rows`
(`PackedFloat32Array`, 9 floats, row-major) and `has_basis: bool`.

**Why a flag and not a sentinel.** `basis != Basis.IDENTITY` cannot tell "this save
predates the field" from "this object's basis genuinely is identity", and
identity is a real state — an unrotated, unscaled cube. The flag makes absence
explicit and survives round-tripping such an object.

**Why no version integer.** The `save-load` skill's checklist wants one. An
`@export` default already provides what a version field would: an old `.tres`
simply lacks `has_basis`, loads with `false`, and takes the untouched
`rotation_degrees * scale` path. Adding a version field would add a migration
step with nothing to migrate. Deliberate, documented deviation.

**Also a deliberate deviation:** the same skill says never use Resources for save
data, because loading an untrusted `.tres` executes embedded GDScript. These
saves are written by the app into `user://models/` and never imported, so the
exposure does not exist here. Not converting to JSON.

Both capture paths now also store the basis, and both restore paths write one
`transform = Transform3D(basis, position)` instead of three separate setters —
so there is a single write path and nothing can drift through the decomposition.

#### 5j-ii. The inspector presented a rotation the user never set

`node.rotation_degrees` runs `Basis.get_euler()`, which is only meaningful on an
orthonormal basis. On a sheared one it returns a number that is not the object's
rotation: **measured 45 -> 33.69 degrees**, an 11.3 degree drift — the same 11.3
degrees the front face tilts. This is the 5h bug family reaching the readout.
Worse, `_on_inspector_rot_changed` rebuilds from `sel.scale`, so writing any of
those fields back flattens the shear to `R*S` with no warning.

Blender does not have this problem: it stores rotation separately, so its Euler
fields never move under shear.

**Decision: disclose, do not block.** A red `ShearWarning` label appears under
Rotation when `_is_sheared(basis)`, and the fields stay editable. Locking them was
considered and rejected — it removes a capability to avoid a confusing number,
and the confusing number is the part that actually needs showing.

`_is_sheared` tests whether the three columns are mutually orthogonal. The
columns are **normalised first**, so the epsilon means the same at any object
size: an absolute dot product scales with the square of the axis lengths, and on a
1000-unit object a raw `1e-6` cutoff would classify clean `R*S` geometry as
sheared. `1e-5` is ~100x the float32 residue a basis picks up crossing
`basis_rows`, so the warning does not flicker across a save.

#### Methodology trap: a test that dies mid-way reported PASS

The first version of this test crashed on a freed node — `restore_model()` frees
the container's children — and **still printed `PASS` and exited 0.** An engine
script error aborts a sub-test without raising anything the test file can see,
and a partial run looks identical to a clean one from outside.

Two fixes, both now permanent in `tests/test_shear_persistence.gd`: every
sub-test that touches a node re-spawns its own cube, and `_done` is counted
against `SUB_TESTS` so a suite with missing sub-tests fails loudly. A test that
did not run is not a passing test.

Verification: `tests/test_shear_persistence.gd` - 6 sub-tests, green after a
6-failure RED with no script errors. Gate after the change: **39 pass, 1 warn
(known-flaky `test_full_lab_sweep`), 0 fail of 40.**

#### 5j-iii. The default was reversed to Local

The measurement above settled the maths; a third report settled the product
question. What was asked for is scale that changes the object's **dimensions
without skewing it**, and Global cannot do that without shear. The designed
fallback was taken up rather than kept in reserve:

`var _orientation: int = Orientation.GLOBAL` -> `Orientation.LOCAL`. One line, as
the comment beside it always claimed. Global is untouched and one click away in
the toolbar, so the two modes can be compared on the same object without
rebuilding anything.

The price, which is not free and is recorded rather than glossed: Local does not
scale to the world-axis size. On the 45-degree-yawed cube with a 1.5 drag,

| | world-X | world-Z | front face | sheared |
|---|---|---|---|---|
| Global | **2.121** | 1.414 | 1.275x1, tilted 11.3 deg | yes |
| **Local (now default)** | 1.768 | 1.768 | 1x1, square | **no** |

A mode that is rectangular *and* reaches 2.121 on world X exists in neither. It is
not built - it was not asked for, and it is not a one-liner - but it is recorded

The argument that settled it is a symmetry worth keeping. Global's case was "the
drawing lies, so make the drawing honest". A Local default inverts that lie - the

### 5k. Snap rounded world components, so a diagonal drag staircased - FIXED

Report: *"the snap function makes the object wiggle"*, raised right after the
Local default landed. It was not the default flip; it was a defect the flip
exposed. Under Local the move axis of any rotated object is diagonal, and
`apply_move` rounded each world component to the grid independently:

```gdscript
var new_pos := _original_positions[i] + move
new_pos = _snap_settings.snap_vector3(new_pos, _snap_settings.position_snap)
```

On an axis-aligned drag this is invisible, because the only component that
changes is the one being dragged. On a diagonal one, X and Z round separately,
each in its own 0.25 steps, at different moments. The object staircases across
the drag line instead of walking along it.

| | before | after |
|---|---|---|
| advances along the axis | `0.217 0.125 0.217 0.342 0.217 0.125 0.217` | all exactly `0.250` |
| strayed off the drag line | up to **0.158** (worst at 60 deg yaw) | **0.000** at every yaw |
| off-grid grab, first frame | `(0.13,0.07,0.11)` -> `(0.25,0,0)` | no movement |
| pair spacing, dragged | `0.7000` -> `0.5000` | `0.7000` held |

Two further defects fall out of the same line and are gone with it. Pressing a
handle used to **teleport** an off-grid object, because the first frame rounded
its existing position rather than the travel. And a multi-selection used to lose
its internal spacing, because each member's already-different original position
rounded to a different delta.

**Fix.** Round the scalar *travel*, not the resulting position. The axis is a
unit vector, so `axis * k * position_snap` is collinear with the drag axis by
construction. `apply_move_delta` (body drag) gets the same rule, since a free 2D
displacement rounds its components the same way.

This makes move consistent with `apply_rotate`, which already snapped the scalar
angle (`transform_manager.gd:127`) — move was the only transform rounding a
vector, which is why this read as a snap bug rather than a move bug. The
axis-aligned case is unchanged: from the origin on a world axis, rounding distance
and rounding the component agree, so ordinary dragging still lands on the grid.
That is asserted as the explicit no-regression guard.

`snap_vector3` is still used for `scale_snap` and is correct there — a scale is
per-axis by nature — so it was left alone.

**The test passed against the broken code for one whole run.** Its first version
swept only 45 degrees of yaw, chosen on the reasoning that 45 was the worst case.
45 is the exact angle that *hides* this defect: the axis is
`(cos45, 0, -sin45)`, so X and Z change by equal and opposite amounts and round
**identically**, keeping every sample exactly on the diagonal. Measured across the
sweep, 45 reports `0.000` off-axis while 20/30/60/70 all report `0.149`-`0.158`.
The test now sweeps 20/30/45/60/70 and keeps 45 only as the case that must not
regress. An angle picked by intuition instead of by measurement concealed the bug
for an entire run — the same trap as 5i-2 and 5g, where a predicted value was
written down before anything measured it.

Verification: `tests/test_snap_uniform.gd` — 6 sub-tests. RED before the fix was
4 failures carrying the numbers in the table above. Gate after: **40 pass, 1 warn
(known-flaky `test_full_lab_sweep`), 0 fail of 41.**
